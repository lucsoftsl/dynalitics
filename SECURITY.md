# Security policy

dynalitics writes analytics, including personal data when a visitor has consented, into **your** database, and can serve a read-only dashboard from it. This page says what we protect, what we deliberately do not, how to report a problem, and which of our promises are backed by a test.

> **Status: pre-release (`0.0.0`, not on npm).** Last audited 2026-10-31 against `docs/SPEC.md` v0.4.2 and the test suite in this repository (re-checked after `tableMode: 'existing'` step 1 landed). Every promise below names the test that fails if it breaks, or says **untested**. Tests run against real PostgreSQL 17 and MySQL 8.4 only. **Nothing is verified on SQL Server** until the `integration (mssql)` job in `.github/workflows/ci.yml` has passed on GitHub (neither workflow has run on GitHub yet).

## Reporting a vulnerability

**Do not open a public issue for a security problem.**

Report it privately through GitHub: **Security tab, "Report a vulnerability"** (private vulnerability reporting) on this repository. The maintainer must enable it first (Settings, Code security); until then use the contact below.

Fallback contact: `<SECURITY CONTACT: the maintainer fills this in before the first release; an email address or a link to a private channel>`

Please include the version, what you expected, what happened, and a minimal reproduction. Do not include real personal data or real credentials.

Response targets (set by the maintainers, **a target and not a promise**; the project is run by a small team): acknowledgement within 5 working days, first assessment within 14 days. We agree a disclosure date with you, credit you if you want, and publish a fix and an advisory.

## Supported versions

Nothing has been published yet. Once released, and while the project is pre-1.0, only the **latest minor version** receives security fixes. Node.js 22 or newer.

## Scope

**In scope:** vulnerabilities in the `dynalitics` and `dynalitics-dashboard` packages as published from this repository, for example:

- SQL injection through visit values, identifiers, custom-field keys, breakdown names, query parameters or the paging cursor
- connection strings, passwords or visitor values leaking through errors, logs, `onError`, `stats()` or HTTP responses
- the read endpoint or dashboard exposing personal data: `authorize` bypass, masking bypass, personal data in a breakdown, a cached response served to the wrong caller
- cross-site scripting through stored visitor strings in the dashboard or React components
- a bypass of the consent gate (personal data stored without consent)
- code execution, prototype pollution, or a weakness in our build and release process (CI, release workflow, published contents)

**Out of scope** (we will still read the report, but it is not a vulnerability in dynalitics):

- Your own configuration: a shared or over-privileged database user, no TLS to the database, no rate limiting on a public endpoint that calls `track()`, an `authorize` function that lets the wrong people in, a weak `ip.salt`, passing an untrusted IP address.
- A compromised host application, host server, database or secret store. dynalitics runs inside your process with your credentials and cannot defend against the code around it.
- A stolen or phished npm account, GitHub account or maintainer machine, or a malicious dependency you install yourself. Provenance and trusted publishing (below) reduce the damage, they do not remove the risk.
- Volumetric denial of service against an endpoint you built.
- Vulnerabilities in `pg`, `mysql2`, `mssql`, `react`, your database or your framework. Report those upstream.
- Anything about features that do not exist yet: `extraColumns` and `dynalitics inspect` are **not built** and carry no guarantee of any kind. `tableMode: 'existing'` is built only as "step 1" (see the non-guarantees).

## Threat model in one page

**What we protect:** the database credential; the personal data in the table; the availability of the host application; the integrity of the statistics. **Trust boundaries:** (a) host code calling `track()` with inputs that are often visitor-controlled; (b) a browser calling the read endpoint; (c) the package talking to the database; (d) the npm supply chain. The full table (T1 to T25) is `docs/SPEC.md` section 11.

| Attacker                                                       | What we do                                                                                                                                                         | What we do not do                                                                                                               |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| A visitor who controls what `track()` receives                 | Bind every value as a parameter, validate and size-limit every field, strip control and bidi characters, cap the queue                                             | Authenticate the visitor, stop forged or flooded events (rate-limit your endpoint), judge whether a visitor really gave consent |
| A person who can reach the read endpoint without being allowed | `authorize` must exist and return strictly `true` first, for every path; fixed queries only; masked output; no CORS headers, no cookies                            | Know who your admins are. A weak `authorize` is your hole, not ours                                                             |
| An allowed dashboard user who wants more than they should see  | Mask personal values unless three independent conditions hold; never accept SQL, columns, sort orders or filters; cap ranges, page sizes, concurrency and run time | Stop an allowed user from reading what the reader credential can read (see non-guarantees)                                      |
| A hostile string stored earlier, rendered later                | Render every API string as text, strict CSP with per-request nonce, `frame-ancestors 'none'`                                                                       | Test in a real browser (jsdom only, see below)                                                                                  |
| Someone who steals the web process's credential                | Writer is `INSERT`-only, so it cannot read back the personal data                                                                                                  | Help if you run one all-powerful credential                                                                                     |
| A malicious or compromised package in the supply chain         | No runtime dependencies, pinned dev dependencies, no install scripts, provenance                                                                                   | Protect you from a compromised npm account or a poisoned driver you installed                                                   |

## Least-privilege setup: two credentials

Use two database users and keep them apart:

| User       | Used by                                 | Privilege on the table | Notes                                                                                      |
| ---------- | --------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------ |
| **writer** | your web process (`track()`)            | `INSERT` only          | Cannot read the data back. On PostgreSQL a `serial` id also needs `USAGE` on its sequence. |
| **reader** | the dashboard process (`createHandler`) | `SELECT` only          | **Can see every personal column.** Protect this credential like the data itself.           |

`npx dynalitics sql --dialect <d> --table <t> --grants-only --writer <role> --reader <role>` prints the `GRANT` statements; dynalitics never runs them and never creates users. dynalitics itself sends no DDL (see the guarantee table). A single credential works for prototypes and logs a warning at startup; with one credential a compromised web process can read all personal data.

Also: use TLS to the database (`sslmode=require`, `encrypt=true`, MySQL `ssl` options) and keep credentials in a secret manager or environment, never in source control. If several sites share one table, configure `scope` on the read handler so each dashboard reads only its own rows; omitting it logs a warning, and `scope: 'none'` states that reading the whole table is intended.

## Consent semantics (exactly what is stored)

| `consent` given to `track()`                               | Stored                                                                                                                                                   |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `true`                                                     | page, timestamp, `consent = true`, and the IP (per `ip.mode`), user id, username, email and declared custom fields you passed                            |
| `false`                                                    | **page, timestamp and `consent = false` only.** IP, user id, username, email are `NULL`                                                                  |
| absent or `null`, no default resolver                      | same as `false` (fail closed); reported once a minute as `consent_missing`                                                                               |
| absent or `null`, `consent.default` returns `true`         | same as `true`                                                                                                                                           |
| absent or `null`, resolver throws or returns a non-boolean | same as `false`; reported as `consent_resolver_failed`                                                                                                   |
| **a non-boolean value** (`'yes'`, `1`, `{}`, ...)          | **never coerced.** Stored as `false` (page, timestamp, `consent = false`), reported as `invalid_visit`. The event is not rejected, so counts stay right. |

Two exceptions to "only page, timestamp and `consent = false`", both opt-in by you:

1. A custom field declared `personal: false` **and** `keepWhenDenied: true` is kept on denied rows. Without `keepWhenDenied`, no custom data survives a denial.
2. Constant extra columns (`extraColumns` with a `constant`) would be written on every row, including denied ones. **`extraColumns` is not built yet** (config rejects it as "not supported yet"), so today there are none.

Limits of the consent gate: dynalitics enforces the boolean you hand it. It does not collect consent, record when or how it was given, or know your legal basis. **The page path is stored on denied rows and can itself identify someone** (`/users/42`, `/reset/<token>`): query strings and fragments are stripped, absolute URLs are reduced to their path and `;matrix` parameters are removed, (`unit/build-row.test.ts`), but use the `page.normalize` hook to map routes to templates. Page plus timestamp is the least we store, not a guarantee of anonymity.

## What we do NOT guarantee

Read this section before relying on dynalitics for anything that matters.

- **Hashed and truncated IP addresses are still personal data** under GDPR and similar laws, as are user ids, usernames and emails. dynalitics cannot make them anonymous, and nothing here is legal advice. Lawful basis, consent collection, retention and **erasure are the host's job**: there is no delete or export path, and the table is yours.
- **SQL Server has never run on a real server.** The dialect, driver, grants and queries are unit-tested with mocks only. Treat SQL Server as unsupported until the `integration (mssql)` job is green.
- **Timeouts on a host-supplied pool are best effort and client-side.** Server-side cancellation is tested only for pools dynalitics creates (PG and MySQL). If you pass your own `pool`, also set `statement_timeout` (PostgreSQL), `max_execution_time` (MySQL) or a query governor (SQL Server) on the reader role.
- **Delivery is at-least-once, in memory.** A retried batch can **duplicate rows** (the first attempt may have been committed even though the client saw an error), and a crash or `kill -9` loses everything still queued. Serverless: `await dyn.flush()` before returning.
- **Masking happens in Node after the query.** The reader credential, and the dashboard process memory, hold the real values. Masking protects the screen and the JSON, not a compromised reader process.
- **The reader credential can see every personal column.** Protecting it is on you. The same is true of anyone with database access.
- **`authorize` is yours.** We enforce that it exists and answers strictly `true`; we cannot tell whether the people it lets in should be there. We also do not rate-limit the endpoint.
- **No CORS and no CSRF code exists.** The posture is by omission: `GET` only, nothing is changed, no cookies are set, no CORS headers are sent. There is no CSRF test. Cross-origin use needs your own CORS layer.
- **Privilege and structure checks at startup are best effort and advisory.** They can miss privileges granted through roles or groups and can be wrong. They never block startup and are not a guarantee that the credential is least-privilege.
- **Real Express and Next.js are simulated, not run.** The adapters are tested with plain Node HTTP and the Fetch `Request`; the code in `docs/read-api-examples.md` is neither compiled nor tested.
- **The dashboard is tested in jsdom, not in a real browser, and has no automated accessibility audit.** The page also works only with ambient credentials (same-origin cookie), not with an `Authorization` header; the React components take `getRequestInit` for that.
- **Provenance and trusted publishing prove where a package was built, not that the code is benign.** They do not protect against a stolen npm account or a compromised maintainer machine; the first version of a package published by hand has no provenance.
- **`mssql` pulls in a large transitive dependency tree.** That is a consequence of choosing SQL Server, not something dynalitics adds.
- **`tableMode: 'existing'` is step 1 only.** Role mapping, type-tolerant checks and the NOT NULL check are tested on real PostgreSQL and MySQL (`integration/existing-table.test.ts`). Not tested: SQL Server; a non-UTC database session with a naive PostgreSQL timestamp (the test containers run in UTC, so a wrong conversion would not show); `datetimeoffset` (statement text only). Existing tables hold rows whose consent semantics dynalitics did not write: a `NULL` or non-boolean legacy consent value is read as denied, but legacy rows may already contain personal data that no consent gate ever saw, and masking applies to them only on read.
- **Not built, no guarantee:** `extraColumns` (constants and computed values), `dynalitics inspect`, views, legacy identifiers outside the strict pattern. If a document says otherwise, the document is wrong.

## Supply-chain posture

What exists in this repository today (checked 2026-10-31):

- **No runtime dependencies** in `dynalitics` and `dynalitics-dashboard` (`dependencies` is absent). Each adapter package (`dynalitics-postgres`, `dynalitics-mysql`, `dynalitics-mssql`) has exactly one runtime dependency, its driver, pinned to an exact version; the release check enforces this. You install only the adapter you use. `react` and `react-dom` are optional peers of the dashboard.
- **Exact version pins** for every development dependency, a committed `package-lock.json`, and `.npmrc` with `ignore-scripts=true`, `save-exact=true`, `engine-strict=true`. CI installs with `npm ci`. **Peer dependency ranges are intentionally wide** (`pg ^8`, `mysql2 ^3`, `mssql ^12`); we test only the latest versions.
- **No install-time scripts** in the packages; `scripts/check-release.mjs` fails the build if one appears.
- **GitHub Actions are pinned to full commit SHAs** (`actions/checkout` v7.0.1, `actions/setup-node` v7.1.0, both verified against the upstream tags), and workflows use `permissions: contents: read` and no secrets.
- **Publishing** is designed to run from `release.yml` with `npm publish --provenance` through **npm trusted publishing (OIDC)** behind a manually approved GitHub environment. **No npm token is stored** in the repository or in GitHub secrets. Publishing and `git commit` are done by a human maintainer.
- `npm audit --audit-level=high` and a published-contents check run in CI. The published tarball is limited to `dist/`, `package.json`, `README.md` and `LICENSE`.

**Not yet true, and untested:** neither workflow has ever run on GitHub; the npm trusted publisher and the `npm-publish` environment are one-time setup the maintainer still has to do; no package has been published, so there is no provenance statement to check yet. See [`docs/RELEASING.md`](docs/RELEASING.md).

## Hardening checklist for people who deploy it

1. Two database users: writer `INSERT` only, reader `SELECT` only. Never use an owner or admin account.
2. TLS to the database. Credentials from a secret manager or environment variables.
3. A real `authorize` function: deny by default, return exactly `true` (or `{ allowed: true }`), and put rate limiting in front of the read endpoint **and** of any endpoint that calls `track()`. Leave `pii.reveal` off unless you need it.
4. Set `scope` on the read handler if the table is shared.
5. Pass the client IP yourself from a trusted proxy setting. dynalitics never reads `X-Forwarded-For`.
6. Prefer `ip.mode: 'truncate'` (default) or `'hash'` with a long, secret salt over `'raw'`. All three are personal data.
7. Use `page.normalize` if your URLs contain ids or tokens. Do not put personal data in `pageVisited`.
8. Plan retention and deletion before you store personal data. Write the `DELETE` job yourself; dynalitics will not.
9. If you pass your own database pool, set a server-side statement timeout on the reader role.
10. Pin and audit your own dependencies and install with `npm ci --ignore-scripts`.
